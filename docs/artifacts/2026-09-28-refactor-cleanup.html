Youki · Engineering update · 28 Sep 2026

A cleaner forecast flow, from location to screen.

A focused refactor of the app’s data lifecycle, API boundaries, account UI, and settings. The existing visual design and public forecast contracts stay in place.

Implementation complete 10 km reuse radius 30 min freshness window

What changed

The work addresses places where duplicated logic or ambiguous state could waste requests, show stale data, or imply a feature that does not exist.

  • ✓Same-area location checks reuse a fresh forecast; moving beyond 10 km requests data for the new coordinates.
  • ✓Sky and score freshness now have separate state, so a failed score refresh cannot present an older score as current.
  • ✓Repeated transport, route validation, and provider timestamp parsing now use shared helpers.
  • ✓Account views are split by responsibility, and Settings labels describe the controls that are actually available.
10 km same-area cache radius The app checks a fresh device fix on load and foreground return. Normal 30-minute and local-day refresh rules still apply.

Implementation

Six cleanup areas

These are contained refactors. The forecast API shapes, endpoint paths, and account actions remain compatible.

01Location state

Reuse nearby forecasts

Device-location mode checks a new fix when the app loads or returns to foreground. Results are reused inside the 10 km radius while fresh; a successful refresh resets the location anchor. Manual coordinates remain selected until the user switches back.

02Freshness

Keep sky and score honest

Initial load and refresh use shared scene and score matching helpers. Partial success keeps usable sky details, while a failed score refresh clears the old score and reports the partial result.

View model regression cases →
03iOS networking

Share authenticated POST setup

Both forecast clients use one JSON POST transport and server-error decoder. Endpoint DTOs, paths, success validation, bearer auth, and AuthSession token handling remain in place.

View shared transport →
04Backend boundary

Validate requests consistently

The prediction and timeline routes share JSON, location, and date validation. Arrays are rejected as objects, and dates must exist on the calendar, including leap-year rules.

View request validation →
05Provider parsing

Preserve local timestamp meaning

Weather, air-quality, and solar adapters share one strict local timestamp helper. It accepts minute or second precision and rejects malformed or timezone-marked values instead of silently relabeling UTC as local time.

View timestamp helper →
06Account & settings

Make ownership and controls clear

Account entry and management are separate views, coordinated by AccountScreen. The settings sheet says “Sunset alerts — Coming later” and labels the location navigation as “Locations.”
