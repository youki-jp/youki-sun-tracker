Youki technical explainer

How the live sky gradient works

The demo does not choose one canned mood such as vivid or pastel. It synthesizes a vertical sky from the sun's current elevation and the atmosphere around it, then emits a stable set of colors that SwiftUI can render and animate.

Repository status: the implementation currently lives in the unmerged origin/feature/gradient-features branch and the separate youki-prototype/gradient.html reference. The Bun backend timeline work is present there; the Swift generator is still a handoff, not yet implemented in the iOS target.

1. The end-to-end data flow

1

Location

Latitude, longitude, optional altitude, and target local date.

2

Solar geometry

The backend calculates elevation, azimuth, twilight crossings, and solar milestones.

3

Atmosphere

Open-Meteo supplies hourly cloud, visibility, humidity, rain, aerosol, dust, and PM2.5 data.

4

Join and interpolate

Solar and atmospheric rows use different grids, so values are interpolated at the render time.

5

Generate sky

generateSky(sample) returns stops, glow, and cloud-band geometry.

Recommended ownership: Bun/Hono owns location normalization, external API calls, solar geometry, and the raw timeline. The gradient generator is presentation logic and can live in SwiftUI. If multiple clients need identical output, it can also be ported to TypeScript and exposed as an optional server-rendered model.

2. What the generator calculates

A. Daylight and glow

dayF transitions from night to day between roughly -8 and 10 degrees of sun elevation. highSun adds gradual midday variation from 10 to 60 degrees. glowF is a Gaussian-like curve centered just below the horizon, so the warmest band appears near sunrise and sunset instead of remaining gold all day.

dayF = smoothstep(-8, 10, elevation)
highSun = smoothstep(10, 60, elevation)
glowF = exp(-((elevation + 1) / 8)^2)

B. Atmospheric modifiers

Cloud layers are treated differently. Low cloud can block the horizon; high cloud can catch warm light and improve the scene. Aerosol, dust, and PM2.5 warm the long light path. Humidity, low visibility, and rain wash contrast toward a softer result.

blocked = clamp01((lowCloud - .30) / .60)
highCatch = bell(highCloud, .15, .60)
wet = clamp01(precipitation / 1.5)

C. Cool zenith anchor

The top of the frame starts from a blue-gray zenith. Its lightness increases with daylight and overcast conditions. Its chroma is high for a clear midday sky and reduced by cloud, aerosol, and haze.

topL = f(dayF, highSun, overcastF)
topC = f(clearChroma, cloudTotal, haze)
topH = 250 + warmTint * lowSunTint

D. Warm horizon anchor

The bottom of the frame is a separate horizon color. Its warmth is controlled by warmVigour, which combines the sun's low elevation with cloud blockage, haze, and precipitation. At midday the warm presence fades, leaving a pale atmospheric horizon.

warmVigour = glowF * (1 - .60 * blocked)
* (1 - .42 * haze) * (1 - .80 * wet)

E. The color path

The generator interpolates the cool and warm anchors in rectangular Oklab coordinates. This allows the path to pass through low chroma instead of forcing a blue-to-gold transition through an unwanted green hue. A controlled magenta bulge is added only when low-sun aerosol or high cloud supports it.

bulge = pink * .086 * sin(pi * t)^1.4
pink = f(aerosolWarm, highCatch, glowF, blocked, wet)

F. Display-safe output

Oklab/Oklch values are converted to sRGB hex. If a color falls outside the sRGB gamut, chroma is reduced iteratively instead of clipping RGB channels, which would shift warm hues.

3. Output model

The output is intentionally stable. Every generated sky has nine stops, even when some conditions are missing or the scene is night. Stable shape matters because SwiftUI can interpolate two gradients smoothly only when their stop counts remain the same.

Vertical sky stops

STOP_POSITIONS = [
  0.00, 0.16, 0.32, 0.46, 0.60,
  0.72, 0.83, 0.93, 1.00
]

stops: [
  { hex: "#526B8A", position: 0.00 },
  // ... exactly nine total
  { hex: "#FFD17A", position: 1.00 }
]

Additional visual layers

glow: {
  centerX: 0.5,
  centerY: 0.89,
  radius: 0.30,
  intensity: 0.42
}

cloudBands: [{
  y: 0.16,
  height: 0.13,
  hex: "#8A96A4",
  opacity: 0.24,
  blur: 0.055
}]

The ramp output is a five-color sample of the same vertical sky and is suitable for the existing color-analysis card. A separate dayRamp can be made by sampling one stop at several times from midnight to midnight.

The reference generator receives one flattened sample. Its renderer should receive finite values, even when the upstream API returns null. Keep nulls in the domain response for confidence and diagnostics; apply renderer defaults only immediately before generation.

5. Why the timeline endpoint is necessary

The existing prediction endpoint returns a sunrise or sunset score and a short event window. That is enough for a summary card, but not enough to render a sky that changes as the user scrubs through a whole day.

Use this endpoint

POST /api/v1/sky-day/timeline
Content-Type: application/json

{
  "location": {
    "latitude": 35.4437,
    "longitude": 139.638,
    "altitudeMeters": 40
  },
  "targetDateIso": "2026-09-05"
}

Response shape

{
  "location": { "timezoneId": "Asia/Tokyo" },
  "targetDateIso": "2026-09-05",
  "milestones": { "sunriseIso": "...", "sunsetIso": "..." },
  "solar": [{
    "timeIso": "2026-09-05T05:16:00",
    "elevationDegrees": -0.27,
    "azimuthDegrees": 80.8,
    "isRising": true,
    "phase": "goldenHourAm"
  }],
  "weather": [{ "timeIso": "...", "cloudCover": {} }],
  "airQuality": [{ "timeIso": "...", "aerosolOpticalDepth": 0.21 }],
  "summary": { "sunriseScore": 22, "sunsetScore": 51 }
}

Different grids are intentional. Solar samples are adaptive and dense around twilight; weather and air quality are hourly. At a render time, interpolate numeric fields between the two bracketing rows. Carry categorical fields such as phase and isRising from the nearer row.

Time-zone rule: the timeline's timeIso strings are naive local wall-clock values. They are local to location.timezoneId, not UTC instants. On the server, use the existing local-time conversion helper; on iOS, decode components with the returned time zone. Do not blindly call Date.parse() on them.

6. Integrating it into the Bun/Hono backend

The gradient can be integrated in two ways. The first keeps the architecture clean and is recommended for Youki. The second is useful when the server must guarantee identical output for web, iOS, and other clients.

Option A: backend serves data, client renders

Keep SkyDayTimelineService as the source of truth for data. Port generateSky() to Swift and call it from the iOS view model. The backend does not need to know about SwiftUI rendering details.

Best when the gradient is a presentation concern and iOS should remain responsible for visuals.

Option B: backend returns a generated model

Port the pure generator to TypeScript, interpolate one timeline sample at a requested atIso, and return stops, ramp, glow, and cloudBands from a dedicated endpoint.

Best when multiple clients need byte-for-byte consistent sky output.

6.3 Flatten and default one interpolated timeline sample

const DEFAULTS = {
  cloudTotalPct: 0,
  cloudLowPct: 0,
  cloudMidPct: 0,
  cloudHighPct: 0,
  visibilityMeters: 24_000,
  relativeHumidityPct: 60,
  precipitationMillimeters: 0,
  aerosolOpticalDepth: 0.08,
  dustUgM3: 0,
  pm25UgM3: 0,
};

function flattenAt(timeline: SkyDayTimelineResponse, atIso: string) {
  const solar = interpolateSolar(timeline.solar, atIso);
  const weather = interpolateWeather(timeline.weather, atIso);
  const air = interpolateAir(timeline.airQuality, atIso);

  return {
    ...DEFAULTS,
    elevationDegrees: solar.elevationDegrees,
    cloudTotalPct: weather.cloudCover.totalPct ?? DEFAULTS.cloudTotalPct,
    cloudLowPct: weather.cloudCover.lowPct ?? DEFAULTS.cloudLowPct,
    cloudMidPct: weather.cloudCover.midPct ?? DEFAULTS.cloudMidPct,
    cloudHighPct: weather.cloudCover.highPct ?? DEFAULTS.cloudHighPct,
    visibilityMeters: weather.visibilityMeters ?? DEFAULTS.visibilityMeters,
    relativeHumidityPct:
      weather.relativeHumidityPct ?? DEFAULTS.relativeHumidityPct,
    precipitationMillimeters:
      weather.precipitationMillimeters ?? DEFAULTS.precipitationMillimeters,
    aerosolOpticalDepth:
      air.aerosolOpticalDepth ?? DEFAULTS.aerosolOpticalDepth,
    dustUgM3: air.dustUgM3 ?? DEFAULTS.dustUgM3,
    pm25UgM3:
      air.particulateMatter2_5UgM3 ?? DEFAULTS.pm25UgM3,
  };
}

The reference uses the same defaults at its rendering boundary. Missing provider values should still remain null in the API response, so prediction confidence and diagnostics are not falsely inflated.

6.4 Interpolation rule

function lerp(a: number, b: number, t: number): number {
  return a + (b - a) * t;
}

// Pseudocode. Compare local wall-clock values in the response timezone.
function interpolateNumeric(rows, atIso, keys) {
  const [before, after] = bracketRows(rows, atIso);
  if (!before) return after;
  if (!after) return before;

  const span = timeDistance(before.timeIso, after.timeIso);
  const t = span === 0 ? 0 : timeDistance(before.timeIso, atIso) / span;
  return Object.fromEntries(keys.map((key) => [
    key,
    lerp(before[key], after[key], t),
  ]));
}

// Categorical values are carried from the nearer row:
phase = t < 0.5 ? before.phase : after.phase;
Important existing limitation: the feature branch's prediction alignment still uses nearest samples for scoring. That is acceptable for the current heuristic score, but not for a smooth gradient. The timeline client or a new shared backend helper must interpolate atmospheric values between the bracketing hours.

7. Porting the generator safely

Keep these constants identical

Stop positions, daylight thresholds, glow curve, cloud blockage, warm spread, Oklab matrices, chroma reduction factor, and magenta bulge are calibrated values. Copy the reference into a pure TypeScript module before changing behavior.

Do not interpolate in sRGB

Interpolating a blue-to-gold ramp directly in RGB produces muddy intermediate colors. Use the reference's Oklab/Oklch path, then flatten each stop to ordinary sRGB hex for the client.

Keep geometry fractional

y, cloud height, blur, glow center, and glow radius are fractions of the actual sky height. This keeps the collapsed 266 point view and full-screen expanded view visually aligned.

Handle polar locations

Milestones such as civil dawn or sunset may be null. A day timeline must not force-unwrap them. The sky generator itself can still render from solar elevation samples when a named milestone does not exist.

9. Recommended implementation order for this repository

  1. Bring the three commits from origin/feature/gradient-features into the working branch, resolving documentation and domain-file conflicts with the current uncommitted integration work.
  2. Keep POST /api/v1/sky-day/timeline as the canonical raw-data contract.
  3. Add shared, timezone-safe interpolation. Do not use nearest-hour values for the visual gradient.
  4. Choose Option A first: port the pure generator to Swift and feed it timeline samples through the existing view-model seam.
  5. Add the server-rendered /gradient endpoint only if web and iOS need identical generated colors or if server-side caching is valuable.
  6. Capture more real sky references for partly cloudy conditions and deep twilight before tuning constants. Those are the reference implementation's stated gaps.
